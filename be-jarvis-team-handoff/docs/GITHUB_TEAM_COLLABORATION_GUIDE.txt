비자비스 GitHub 팀 협업 가이드
===============================

작성일: 2026-08-24
저장소: https://github.com/hyeok18/Be-Jarvis


1. 가장 먼저 알아야 할 것
-------------------------

GitHub는 팀이 함께 사용하는 인터넷상의 공용 프로젝트 보관소입니다.
각 팀원의 컴퓨터에는 GitHub 프로젝트의 개인 복사본이 있습니다.

누군가 GitHub에 파일을 push하면:

1) GitHub에 있는 파일은 변경됩니다.
2) 다른 팀원의 컴퓨터 파일은 바로 변경되지 않습니다.
3) 다른 팀원이 pull해야 변경된 파일을 받을 수 있습니다.

간단히 기억하면 다음과 같습니다.

push = 내 컴퓨터의 변경사항을 GitHub에 올리기
pull  = GitHub의 최신 변경사항을 내 컴퓨터로 받기


2. 자주 사용하는 용어
----------------------

repository(저장소)
- 프로젝트 파일과 변경 기록을 보관하는 공간입니다.
- 비자비스 저장소 주소는 다음과 같습니다.
  https://github.com/hyeok18/Be-Jarvis

clone(복제)
- GitHub 프로젝트를 내 컴퓨터에 처음 내려받는 작업입니다.
- 컴퓨터마다 최초 한 번만 하면 됩니다.

branch(브랜치)
- main 파일을 바로 수정하지 않고 안전하게 작업하는 개인 작업 공간입니다.
- 사람 또는 작업 단위마다 별도 브랜치를 사용합니다.

commit(커밋)
- 변경사항에 설명을 붙여 하나의 저장 기록으로 만드는 작업입니다.

push(푸시)
- 내 컴퓨터의 커밋을 GitHub에 올리는 작업입니다.

pull(풀)
- GitHub의 최신 커밋을 내 컴퓨터에 받아 합치는 작업입니다.

Pull Request(PR)
- 개인 브랜치의 변경사항을 main에 합쳐 달라고 요청하는 절차입니다.
- 다른 팀원이 변경 내용을 검토하고 승인할 수 있습니다.

merge(병합)
- 검토가 끝난 브랜치의 내용을 main에 합치는 작업입니다.

conflict(충돌)
- 두 사람이 같은 파일의 같은 부분을 다르게 수정해서 Git이 자동으로 합치지 못하는 상태입니다.


3. 권장 협업 순서
-----------------

최신 main 받기
→ 개인 작업 브랜치 만들기
→ 구현하기
→ 테스트하기
→ 개발일지 작성하기
→ commit하기
→ 개인 브랜치를 push하기
→ Pull Request 만들기
→ 다른 팀원이 검토하기
→ main에 merge하기
→ 모든 팀원이 다시 pull하기

중요:
- main 브랜치에서 직접 개발하지 않습니다.
- 한 작업 단위마다 브랜치 하나와 Pull Request 하나를 사용합니다.
- 비자비스의 작업 단위는 WU-01, WU-02처럼 표시합니다.


4. 프로젝트를 처음 받을 때
---------------------------

터미널에서 다음 명령을 실행합니다.

git clone https://github.com/hyeok18/Be-Jarvis.git
cd Be-Jarvis

그다음 다음 문서를 순서대로 읽습니다.

1) AGENTS.md
2) be-jarvis-team-handoff/START_HERE.md
3) be-jarvis-team-handoff/docs/DEVELOPMENT_PRIORITY.md
4) be-jarvis-team-handoff/docs/development-logs/INDEX.md
5) 현재 작업과 관련된 최신 개발일지


5. 새로운 작업을 시작할 때
-------------------------

1) main 브랜치로 이동합니다.

git switch main

2) GitHub의 최신 변경사항을 받습니다.

git pull --ff-only origin main

3) 자신의 작업 브랜치를 만듭니다.

예시:

git switch -c feature/WU-01-esta-schema

브랜치 이름 권장 형식:

기능 개발: feature/WU-번호-짧은설명
버그 수정: fix/WU-번호-짧은설명
문서 수정: docs/WU-번호-짧은설명

예시:

feature/WU-01-esta-schema
fix/WU-06-date-validation
docs/WU-00-github-guide


6. 작업이 끝났을 때
-------------------

1) 변경된 파일을 확인합니다.

git status

2) 테스트를 실행합니다.

작업 단위의 테스트 방법은 다음 문서에서 확인합니다.

be-jarvis-team-handoff/docs/DEVELOPMENT_PRIORITY.md

3) 개발일지를 작성합니다.

개발일지 위치:

be-jarvis-team-handoff/docs/development-logs/

개발일지에는 다음 내용을 적습니다.

- 무엇을 만들었는가
- 무엇이 문제였는가
- 어디에서 막혔는가
- 어떻게 해결했는가
- 어떤 테스트를 했는가
- 테스트 결과는 무엇인가
- 다음 작업에서는 무엇을 해야 하는가

4) 필요한 파일만 commit 대상으로 추가합니다.

예시:

git add public/esta-schema.js
git add be-jarvis-team-handoff/docs/development-logs/작성한파일.md

가능하면 git add . 대신 수정한 파일을 직접 지정합니다.
이렇게 하면 .env나 불필요한 파일이 실수로 올라가는 것을 줄일 수 있습니다.

5) commit을 만듭니다.

예시:

git commit -m "feat: implement WU-01 ESTA schema"

6) 개인 브랜치를 GitHub에 push합니다.

git push -u origin feature/WU-01-esta-schema


7. Pull Request 만드는 방법
---------------------------

1) GitHub의 비자비스 저장소로 이동합니다.
   https://github.com/hyeok18/Be-Jarvis

2) 방금 push한 브랜치의 Compare & pull request 버튼을 누릅니다.

3) base 브랜치가 main인지 확인합니다.

4) 제목을 다음과 같이 작성합니다.

[WU-01] 공식 ESTA 질문 스키마 확정

5) 설명에는 다음 내용을 작성합니다.

- 구현한 내용
- 변경된 파일
- 테스트 방법과 결과
- 발견한 문제와 해결 방법
- 남은 위험
- 개발일지 링크

6) 다른 팀원 한 명을 Reviewer로 지정합니다.

7) 검토자가 승인하고 테스트가 통과하면 main에 merge합니다.


8. 다른 사람의 작업이 main에 합쳐진 후
--------------------------------------

모든 팀원은 다음 작업을 시작하기 전에 최신 main을 받아야 합니다.

git switch main
git pull --ff-only origin main

사용이 끝난 로컬 작업 브랜치는 삭제할 수 있습니다.

git branch -d feature/WU-01-esta-schema


9. 누군가 main에 직접 push했다면
--------------------------------

GitHub의 main 파일은 바로 변경됩니다.
다른 팀원의 컴퓨터에는 아직 이전 파일이 남아 있습니다.

다른 팀원은 다음 명령으로 변경사항을 받습니다.

git switch main
git pull --ff-only origin main

하지만 여러 사람이 main에 직접 push하면 충돌과 실수가 생기기 쉽습니다.
따라서 main 직접 push 대신 개인 브랜치와 Pull Request를 사용합니다.


10. 파일 충돌을 줄이는 방법
---------------------------

- 작업을 시작하기 전에 항상 main을 pull합니다.
- 팀 채팅이나 GitHub Issue에서 담당 WU를 먼저 정합니다.
- 같은 작업 단위를 두 명이 동시에 별도로 수정하지 않습니다.
- 같은 파일을 동시에 수정해야 한다면 담당 구역을 미리 나눕니다.
- 큰 변경을 한 번에 올리지 말고 작은 작업 단위로 나눕니다.
- Pull Request가 오래 열려 있으면 최신 main을 작업 브랜치에 반영합니다.
- 충돌이 나면 상대방의 코드를 임의로 삭제하지 않습니다.

작업 브랜치에 최신 main을 반영하는 기본 방법:

git fetch origin
git merge origin/main

충돌 파일이 표시되면 팀원과 함께 어느 내용을 유지할지 결정합니다.
충돌을 해결한 후 전체 테스트를 다시 실행합니다.


11. pull하기 전에 내 수정사항이 남아 있다면
--------------------------------------------

먼저 다음 명령으로 상태를 확인합니다.

git status

수정사항이 있다면 바로 pull하지 말고 다음 중 하나를 선택합니다.

방법 1) 작업이 의미 있는 상태라면 commit합니다.

방법 2) 작업이 아직 불완전하다면 해당 작업 브랜치에서 계속 작업합니다.

방법 3) 임시 보관이 꼭 필요하면 Git 사용 경험이 있는 팀원과 stash 사용을 상의합니다.

다른 팀원의 작업을 잃을 수 있으므로 다음 명령은 함부로 사용하지 않습니다.

git reset --hard
git push --force

특히 main에는 강제 push를 하지 않습니다.


12. main 브랜치 보호 설정
-------------------------

저장소 관리자는 GitHub에서 다음 경로로 이동합니다.

Settings
→ Rules
→ Rulesets
→ New ruleset
→ New branch ruleset

권장 설정:

- 대상 브랜치: main
- Require a pull request before merging
- 승인 인원: 1명
- Require conversation resolution
- Block force pushes
- main 브랜치 삭제 제한
- 자동 테스트가 만들어진 후 Require status checks 활성화

GitHub 요금제나 저장소 공개 여부에 따라 일부 메뉴가 다를 수 있습니다.
Rulesets를 사용할 수 없다면 Branch protection 메뉴를 확인하거나 팀 규칙으로 main 직접 push를 금지합니다.


13. 비자비스 팀 전용 작업 규칙
------------------------------

1) DEVELOPMENT_PRIORITY.md에서 현재 작업 단위를 확인합니다.

2) 진행 중 또는 다음으로 표시된 WU 하나만 작업합니다.

3) 작업 브랜치 이름에 WU 번호를 포함합니다.

4) 구현만 끝났다고 완료 처리하지 않습니다.
   구현, 테스트, 검증, 개발일지 작성이 모두 끝나야 완료입니다.

5) 작업 단위가 완료되면 같은 세션에서 다음 WU를 자동으로 시작하지 않습니다.
   다음 세션이 이전 개발일지를 읽고 이어서 진행합니다.

6) Pull Request에는 코드와 해당 개발일지를 함께 올립니다.

7) 공식 ESTA 정보는 미국 정부 공식 출처로 확인하고 URL과 확인일을 기록합니다.

8) 실제 개인정보를 테스트하거나 GitHub에 올리지 않습니다.

9) 다른 국가 또는 다른 비자 기능은 현재 ESTA MVP가 KPI를 통과한 뒤 시작합니다.


14. Codex에 작업을 맡길 때 사용할 문장
---------------------------------------

아래 문장을 복사해 Codex에 입력할 수 있습니다.

이 저장소의 AGENTS.md를 먼저 끝까지 읽어라.
그다음 be-jarvis-team-handoff/docs/DEVELOPMENT_PRIORITY.md와
development-logs/INDEX.md, 현재 작업 단위의 최신 개발일지를 읽어라.
진행 중인 작업이 있으면 그것을 이어서 수행하고, 없다면 다음으로 표시된
WU 하나만 구현하라. 구현 후 작업 단위에 정의된 테스트와 검증을 실행하고,
개발일지를 작성한 뒤 다음 WU는 시작하지 말고 결과를 보고하라.


15. 절대 GitHub에 올리면 안 되는 것
-----------------------------------

- .env 파일
- OpenAI API 키
- 비밀번호와 인증 토큰
- 실제 이름, 생년월일, 주소, 전화번호
- 실제 여권번호와 여권 사진
- 실제 ESTA 신청 내용
- 서버 로그에 포함된 개인정보
- node_modules 같은 대용량 설치 폴더

push 전에는 항상 git status로 올라갈 파일을 확인합니다.


16. 가장 짧은 작업 체크리스트
--------------------------------

작업 시작:

[ ] git switch main
[ ] git pull --ff-only origin main
[ ] 담당 WU 확인
[ ] 개인 브랜치 생성
[ ] 이전 개발일지 확인

작업 종료:

[ ] 구현 완료
[ ] 테스트 통과
[ ] 개발일지 작성
[ ] git status 확인
[ ] 필요한 파일만 commit
[ ] 개인 브랜치 push
[ ] Pull Request 생성
[ ] 팀원 검토 및 승인

PR이 merge된 후:

[ ] git switch main
[ ] git pull --ff-only origin main
[ ] 다음 작업은 최신 개발일지를 읽은 후 시작
